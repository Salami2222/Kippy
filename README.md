# MacroMellow: AI-powered nutrition assistant

MacroMellow is a local prototype of an AI-powered nutrition assistant. Its chat agent is **Mellow**: tell Mellow what you ate, ask about a meal, or track daily macros through conversation. Its **current official nutrition source is UMD dining only**: the [UMD Dining nutrition site](https://nutrition.umd.edu/) for South Campus Dining Hall, Yahentamitsi (The Y), and 251 North. Mellow can interpret a meal request through Ollama on a separate computer, match saved UMD foods, and calculate totals in Python. The food data browser remains available even when Ollama is offline. No official nutrition values are generated by the model. Other dining halls, restaurants, and estimated foods are future goals, not supported data sources in this prototype.

## Set up Ollama on the Windows desktop

1. Install [Ollama for Windows](https://ollama.com/download/windows) on the desktop and install [Tailscale](https://tailscale.com/download) on both the desktop and MacBook. Sign both devices in to the same tailnet.
2. On **Windows**, open PowerShell and run `ollama pull qwen3.5:9b`. Verify it appears in `ollama list`.
3. By default Ollama listens only on `127.0.0.1`. On **Windows**, quit Ollama from its taskbar icon. In Windows environment variable settings, create the user variable `OLLAMA_HOST` with value `0.0.0.0:11434`, then restart Ollama from the Start menu. Limit inbound TCP port 11434 to the Tailscale network in Windows Firewall; do not expose the port to the public internet.
4. Find the desktop's Tailscale IP or MagicDNS name in the Tailscale app or admin console. On the **MacBook**, test `curl http://YOUR-WINDOWS-TAILSCALE-IP:11434/api/tags`. The JSON should include a model named `qwen3.5:9b`.
5. In the MacBook terminal where you launch MacroMellow, run:

```bash
export OLLAMA_BASE_URL="http://YOUR-WINDOWS-TAILSCALE-IP:11434"
export OLLAMA_MODEL="qwen3.5:9b"
```

Replace the placeholder with the actual Tailscale IP or MagicDNS name. The defaults are `http://localhost:11434` and `qwen3.5:9b`, so set the remote URL for the Windows setup. Ollama runs on the desktop; there is no Ollama installation step on the MacBook. The app's **Mellow connected** indicator checks `/api/tags` for both reachability and the exact configured model. If it says the model is missing, pull that model on Windows or change `OLLAMA_MODEL` and restart MacroMellow.

These setup steps follow [Ollama's Windows environment variable and network instructions](https://docs.ollama.com/faq), [Ollama's model list API](https://docs.ollama.com/api/tags), and [Tailscale's device connection guide](https://tailscale.com/docs/how-to/connect-to-devices).

## Launch the local web interface

From the repository directory, use Python 3.10+:

```bash
python3 -m macromellow web
```

The server opens [http://127.0.0.1:8000/](http://127.0.0.1:8000/) in your browser. If a browser tab does not open automatically, visit that address yourself. Press `Ctrl+C` in the terminal to stop the server. Use **Chat** to talk with Mellow, **Daily macros** to focus the tracker, and **Food data** to search the currently supported UMD menus and open original labels. On a typical laptop, chat and daily macros share the screen and scroll independently; on smaller screens, the tracker starts as a compact summary above chat. Enter sends a chat message; Shift+Enter adds a line. **New chat** clears the current conversation context. The visual design uses local system fonts, and the small Mellow letter tile is an avatar slot for future mascot artwork.

The app reads actual JSON files in this repository's `data/` directory. Data is not committed to Git, so a fresh clone starts empty: open **Food data**, choose today's date, and click **Refresh UMD data** to retrieve all three halls. A complete refresh can take several minutes; the page shows a loading state and any retrieval error. Existing saved data is kept if a refresh is incomplete. Dates outside UMD's current seven-day menu window cannot be refreshed, although older saved JSON can still be viewed. After a refresh, return to **Chat** and ask about that date.

You can change the local port or data directory:

```bash
python3 -m macromellow web --port 8001 --data-dir /path/to/your/json-directory
```

Use `--no-browser` if you only want to start the server. The server listens on `127.0.0.1` only. It uses Python's standard library and needs no Python package installation step. All model requests go from the Python backend to Ollama; the browser never calls Ollama directly.

### Visual design

The interface uses marshmallow surfaces, a warm cream background, and caramel accents with toasted-brown headings. Shared palette tokens live in `macromellow/static/app.css`; error and success feedback retain distinct colors. Rounded controls use a short squish on press and a gentle spring on release. Chat entrances, progress bars, value updates, and expanding panels animate subtly and respect reduced-motion preferences. No external fonts or UI dependencies are needed; the Mellow avatar slot is preserved for future mascot artwork.

## Daily macro tracker

**Today’s macros** stays beside the assistant conversation on desktop. On smaller screens, a compact four-number summary sits above chat; tap **Show details** or **Daily macros** to open goals and adjustments. Open **Adjust totals manually** to add, subtract, or set any combination of calories, protein, carbs, and fat. Leave a field blank to keep it unchanged; zero is a valid direct value. The four totals are independent, and manual entries can be negative for testing corrections. **Reset to zero** clears the current day's totals.

Open **Edit daily goals** to enter your own calorie, protein, carb, and fat goals. Save any combination; a blank field removes that goal, and zero is allowed. Each card shows the consumed amount, its goal, a progress bar, and the amount remaining or exceeded. Goals and consumed totals are independent: changing protein does not recalculate calories or another macro.

Complete AI nutrition results have an **Add result to today** button. Answering a question does not change tracked totals until you press it or approve its specific thumbs-up offer. You can also explicitly ask the assistant to log a meal. A result is added only once; an incomplete or ambiguous UMD result cannot be logged automatically, but you can enter your own test values manually. Ask the assistant to correct a logged meal to replace its old values, or say “undo” to reverse its last meal change in that conversation.

The tracker, goals, meal history, conversation context, and personal memory now live in SQLite at `data/macromellow.sqlite3` (or inside `--data-dir`). This file is excluded from Git. Totals are calculated from that day's active meal records and manual adjustments. At midnight **America/New_York**, the new day's total is zero; older meal records and goals remain. The open page refreshes at the day change. **Logged meals** lets you review and remove today's records. Tracked values remain **user-adjustable estimates** and may differ from official UMD values.

On first use, the page imports the existing browser-only totals and goals into SQLite once. It keeps a copy under the browser storage key `macromellow.browser-backup.v1`. If backend totals already exist and differ, the app keeps the backend totals and shows a notice instead of silently combining them; the browser backup remains available for review. No account is created: this local prototype uses one `local` profile, with a profile ID on database rows for a later multi-user migration. Keep a copy of the SQLite file if you want to back up your data.

Open **Personal memory** to review, add, edit, or delete preferences, favorites, common meals, and frequently chosen foods. These are user-managed notes separate from meal logs: saving a favorite never changes daily macros. Favorite restaurants are names and preferences only; this version still retrieves nutrition solely from UMD.

## Test the assistant

With a saved menu and the Windows Ollama server connected, ask `How many calories are in 2 servings of grilled chicken breast at 251 North today?` Substitute a food and date present in your saved data. That question does not log a meal. Follow with `Add that to today's macros`, then `Actually, make that 3 servings` to correct the logged entry, or `Undo that correction`. Try `What are my macros today?`, `What meals have I logged?`, and `Remember that I prefer rice at lunch`. The **Personal memory** section is where you can inspect and change saved preferences. If the AI indicator is offline, the UMD data browser and manual tracker still work.

The assistant sends a constrained JSON schema to [Ollama's chat endpoint](https://docs.ollama.com/api/chat) and validates the returned plan. The model identifies the requested operation, foods, portions, halls, dates, and memory fields; it never supplies official nutrient numbers. Python searches saved UMD menus, rejects uncertain matches, multiplies official per-serving values, and calculates totals. Logging requires an explicit add/log/track request, a matching menu date, complete official macro values, and a clear listed portion. A vague portion or uncertain food prompts clarification before the ledger changes. Repeat meal fingerprints are not silently logged twice. Conversation context is a small recent window plus the current meal state stored in SQLite, so it survives a server restart when the browser retains its conversation ID. A new chat starts a separate context.

### Natural meal descriptions and clarification

Mellow accepts multi-food descriptions such as:

> I had a macaroni pizza slice, 2 scoops of cilantro lime rice, 1 chocolate chip cookie and a scoop of mac n cheese

The working meal retains all four reported items: one pizza slice, two scoops of rice, one cookie, and one scoop of mac and cheese. Names are checked against actual saved UMD labels; a missing macaroni pizza does **not** turn into a different pizza. Aliases such as `mac n cheese` and `mac and cheese`, conservative spelling similarity, requested ingredients, token coverage/precision, hall/date filters, and competing labels contribute to matching. Exact duplicate labels listed at multiple halls can share a result; distinct recipes still need a hall or label choice.

A clarification keeps the complete working meal in SQLite: food names, reported quantities/units, selected label keys, remaining unresolved items, the current question, and the intended lookup/log/edit operation and authorization. Reply with a candidate name, a distinguishing description, or **the first one**. Candidate buttons fill a specific reply into the composer. Follow-ups such as **The pizza was from The Y**, **Actually it was 3 scoops of rice, not 2**, and **Wait, remove the cookie** change the relevant item without discarding the rest. If a correction could apply to multiple items, Mellow asks which one. Preferences remain separate from consumed meals.

A scoop is never silently treated as a serving. An exact listed count (e.g. one slice or one each) can be calculated directly; measured weights use standard unit conversions. If a scoop's size is unknown, reply with something like **each scoop was 3 oz** or **each scoop matches one listed serving** if that is accurate. No cup-to-weight density or scoop size is guessed. Cards with uncertain portions show official **per-listed-serving** values only. A clearly labeled **confirmed subtotal** excludes unresolved items/portions, and a complete meal cannot be logged until required matches, portions, dates, and nutrients are verified. Older saved results with assumed scoop conversions must be checked again.

**I had...** performs a lookup, without persistent logging. **Can you add that to today's macros?** explicitly requests logging. A pending explicit log can finish after its portion/label questions are answered; **don't log it** cancels that intent. Corrections replace the existing logged meal, and undo restores both its ledger values and working context. Canonical label/serving fingerprints and request IDs prevent duplicate additions. **I had the same thing as yesterday** requires a unique, real, verified prior meal; historical labels retain their source date, and logging on a new date requires matching records for that date.

#### Local planner reliability

The planning schema requires only `operation`; unrelated fields are optional, and Python normalizes and strictly validates defaults, foods, patches, dates, and types. No source URL or official nutrient values are accepted from the model. A single fenced JSON object is supported. Empty, malformed, truncated, missing, or incorrectly typed model output can receive **one repair request**, within a shared 90-second planning budget. Connection errors, timeouts, HTTP failures, and model failures are reported explicitly and are not retried as interpretations. The model availability check has its own 10-second timeout.

Planning calls use `think: false` and a bounded output budget; this is a per-request option, with no change to Ollama's installation or Windows configuration. In the live October 21 test, `/api/show` reported Qwen's default thinking enabled; the first thinking-enabled request timed out. With thinking disabled, the exact four-food example extracted correctly on the first attempt in about two seconds. A subsequent live five-turn check preserved food context through hall/quantity corrections and removal while leaving daily totals unchanged. These smoke tests used a temporary database and copies of saved menus, not the active tracker.

Developer debugging distinguishes malformed JSON, missing/empty content, invalid fields, truncated output, repair attempts, connection issues, timeouts, and model failures. It also shows pending state, individual match signals, and verified portion calculations. Sanitized failure diagnostics contain categories and field names, without raw model replies or private conversation content in server logs. Normal chat history/debugging remains stored locally in SQLite. See [Ollama's thinking controls](https://docs.ollama.com/capabilities/thinking).

Remaining limits: only saved UMD menus are supported; short/generic names, unknown dishes, ambiguous past meals, and unmeasured portions can still require clarification. Matching scores are conservative heuristics, not calibrated probabilities. An unsupported answer stays unresolved. Model parsing is tested with deterministic fixtures; real Qwen behavior can vary. Restart the app manually after updating to run the changes; no automatic deployment or network configuration changes are performed.

### Message reactions and acknowledgments

Every new chat turn is now saved as messages with stable IDs in the existing SQLite database. The current conversation and its reactions reload after a page refresh or server restart. Older compact agent context is retained, but messages from before this update cannot be reconstructed as a full transcript. **New chat** starts a separate conversation.

- Tap **👍** beneath any Mellow message to add your reaction; tap again to remove it. The button is keyboard accessible and reports its pressed state. Your reaction and Mellow's acknowledgment have distinct labels.
- Mellow attaches **👍 Mellow** to understood requests. This means acknowledgment, **not proof of success**. Questions still receive answers and factual cards. Clarifications and failures show explicit text instead of an acknowledgment. Straightforward manual macro changes show the updated dashboard and a success notification, with debugging details attached to the request.
- A complete, unambiguous, same-day UMD lookup can include **React 👍 to log this meal for YYYY-MM-DD**. Only that visible offer authorizes a reaction-triggered action. The backend binds approval to its exact result, message, conversation, and date. Older offers become stale after a newer Mellow response or midnight. A reaction to a clarification, error, or unrelated message does not execute a tool. Removals, resets, and memory deletion require explicit words or their existing controls.
- Retries, repeated taps, removal/re-addition, and the existing **Add result to today** button cannot log the same result twice. Removing a reaction never undoes a meal; use the existing removal or undo workflow. An interrupted approval is not automatically retried: inspect the tracker before asking again.
- Chat supports literal manual changes such as **Add 35g protein**, **Remove 200 calories from today**, or **Set 100g protein and 60g fat**. These reuse the existing adjustment ledger; calories and macros remain independent. The backend checks model-extracted amounts against the actual request. Ambiguous phrasing or other dates require clarification; the dashboard remains available for more flexible edits.

The Ollama planner now returns a validated response type (`acknowledgment`, `message`, `clarification`, or `action`) alongside its operation. Conversation replies do not bypass deterministic nutrition and action tools. Relevant reaction events include the referenced message ID and text in the bounded conversation context. Invalid model responses produce an explicit error without executing an action. No new dependencies or configuration are needed; restart the Python server after updating the checkout. Automated planner fixtures live only in tests, not in an application mock mode.

Local tests do not verify deployment on the Windows host. Pull the GitHub changes and restart that application's Python process on the host where it runs to deploy them; the Ollama model itself does not need a new installation.

### Developer debugging

Open **Developer debugging** below any assistant response to inspect that turn. It shows the original request, the model's structured interpretation and backend action, the effective meal items after any follow-up correction, the saved date and hall used for each lookup, selected UMD label links, and ranked alternative records. The displayed name score is a **heuristic similarity score, not a probability** that the food is correct. A low score or a close competing record prevents automatic selection and asks for clarification. A different selected menu name or an unresolved portion is called out in the normal response as well as the debug panel.

For each selected food, the panel shows UMD values per listed serving multiplied by the verified serving factor, then the final total. Missing official values remain unavailable in both places. The panel also lists accuracy notes, the Ollama response time (including its model availability check), the full request time, and any error stage. Errors return a debug panel too. These diagnostics appear in the local browser and persisted conversation history; they are not saved to the UMD JSON files.

Run the automated tests without a live Ollama server:

```bash
python3 -m unittest discover -s tests -v
node --test tests/test_tracker.cjs
```

Optionally test the real configured Ollama model, without changing the active tracker:

```bash
python3 tests/smoke_ollama.py
```

This uses a temporary SQLite database and copies of saved JSON menus. It checks the four-food example plus hall/quantity corrections, cookie removal, and a follow-up question. It prints `SKIPPED` when the model is unavailable, and exits unsuccessfully on a failed assertion or model response. Pass a JSON data-directory path as the first argument if needed. The automated suite includes a checked-in excerpt of actual October 19 UMD labels; it does not require live Ollama or a network connection.

## Command line retrieval and search

Python 3.10+ is required. There are no third-party Python dependencies.

```bash
python3 -m macromellow fetch --hall all --output data/latest.json
python3 -m macromellow search "chicken" --file data/latest.json
python3 -m macromellow search "tofu" --file data/latest.json --hall yahentamitsi
```

Omit `--date` to use today's date in Maryland. `--hall` accepts `all`, `south`, `yahentamitsi`, or `251-north`. The default output is `data/umd-YYYY-MM-DD.json`; use `--output` to choose another path. A full fetch follows all linked nutrition labels and may take several minutes. For a quick connectivity check, `--max-labels 3` fetches all requested menus but only three unique labels; skipped labels remain `null` and are recorded as errors. The command returns exit status 2 when the saved result has any errors, and 1 if it cannot start (for example, robots.txt cannot be checked).

Search reads a saved JSON file without making network requests. It displays matching food names, hall, date, meal, serving size, calories, protein, carbohydrates, fat, and the official label URL. Unknown values display as `unknown`.

## Data source and method

UMD's public menu page has an ordinary GET form with `locationNum` and `dtdate`. Its [public JavaScript](https://nutrition.umd.edu/js/custom.js) uses those fields to change the displayed menu and offers a rolling seven-day date selector. The form lists hall IDs 16 (South Campus), 19 (Yahentamitsi), and 51 (251 North). Each menu item links to an individual `label.aspx?RecNumAndPort=...` page. The prototype reads the menu HTML, follows those official links, and extracts the primary Nutrition Facts panel's serving size, calories per serving, total fat, total carbohydrate, and protein. It stores the menu and label URLs with every item. A repeated label URL is fetched only once per run.

I found no publicly documented nutrition API on the official site during the initial investigation (October 19, 2026). This prototype uses the site's public HTML; it does not use a private endpoint or bypass an access restriction. The site's `/robots.txt` returned HTTP 404 when checked. At run time, the program checks it again: explicit disallow rules are honored, while unexpected failures stop retrieval. Requests are sequential with at least 0.25 seconds between them; HTTP 403 or 429 stops the run. The default delay can be increased with `--delay`.

## JSON format

The JSON file contains `schema_version`, `source`, `menu_date`, `retrieved_at`, `foods`, and `errors`. Each `foods` entry contains `dining_hall`, `menu_date`, `meal`, `station`, `name`, `serving_size`, `calories`, `protein_g`, `carbohydrates_g`, `fat_g`, `menu_url`, `source_url`, and `retrieved_at`. Nutrients are **per listed serving**, not per meal. A food can appear more than once if UMD lists it at multiple meals or stations. Numeric fields and serving size are `null` when unavailable; `errors` records inaccessible pages and parsing failures. Saved data is excluded from Git because menus change and a full scrape is relatively large.

## Limits

- UMD's date picker offers today plus six days. Other dates may have no menu; the program reports an empty menu instead of assuming one.
- UMD notes that its nutritional analysis is approximate and can vary with ingredients and preparation. See an [official label](https://nutrition.umd.edu/label.aspx?RecNumAndPort=119370%2A1).
- The parser depends on UMD's current HTML structure. If UMD changes it, fields may become `null`; whole-label parsing failures appear in `errors`. Verify against the site before using the data in another product.
- A partial file may be saved when a request fails. Inspect `errors` before treating a dataset as complete.
- On October 19, 2026, six distinct official labels explicitly said nutrition information was unavailable. They account for 14 menu appearances with `null` nutrition fields in the saved test dataset.
- A menu item may not exist at the requested hall or date. For example, the saved October 19 and 20 menus do not list a chicken breast at The Y. The assistant will request a more specific item or another date instead of using a different chicken dish silently.
- This prototype uses name-based matching against local saved data, not ingredient recognition. Official menus can contain similar dishes; inspect the linked label when a selection matters.
