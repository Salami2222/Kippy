# MacroMellow: UMD nutrition assistant

This local Python prototype retrieves current menu items and per-serving nutrition facts from the [official UMD Dining nutrition site](https://nutrition.umd.edu/). It covers South Campus Dining Hall, Yahentamitsi (The Y), and 251 North. A conversational assistant can interpret a meal request through Ollama on a separate computer, match saved UMD foods, and calculate totals in Python. The manual data browser remains available even when Ollama is offline. No nutrition values are generated by the model.

## Set up Ollama on the Windows desktop

1. Install [Ollama for Windows](https://ollama.com/download/windows) on the desktop and install [Tailscale](https://tailscale.com/download) on both the desktop and MacBook. Sign both devices in to the same tailnet.
2. On **Windows**, open PowerShell and run `ollama pull qwen3.5:9b`. Verify it appears in `ollama list`.
3. By default Ollama listens only on `127.0.0.1`. On **Windows**, quit Ollama from its taskbar icon. In Windows environment variable settings, create the user variable `OLLAMA_HOST` with value `0.0.0.0:11434`, then restart Ollama from the Start menu. Limit inbound TCP port 11434 to the Tailscale network in Windows Firewall; do not expose the port to the public internet.
4. Find the desktop's Tailscale IP or MagicDNS name in the Tailscale app or admin console. On the **MacBook**, test `curl http://YOUR-WINDOWS-TAILSCALE-IP:11434/api/tags`. The JSON should include a model named `qwen3.5:9b`.
5. In the MacBook terminal where you launch MacroMellow, run:

```bash
export OLLAMA_BASE_URL="http://YOUR-WINDOWS-TAILSCALE-IP:11434"
export OLLAMA_MODEL="qwen3.5:9b"
```

Replace the placeholder with the actual Tailscale IP or MagicDNS name. The defaults are `http://localhost:11434` and `qwen3.5:9b`, so set the remote URL for the Windows setup. Ollama runs on the desktop; there is no Ollama installation step on the MacBook. The app's **AI connected** indicator checks `/api/tags` for both reachability and the exact configured model. If it says the model is missing, pull that model on Windows or change `OLLAMA_MODEL` and restart MacroMellow.

These setup steps follow [Ollama's Windows environment variable and network instructions](https://docs.ollama.com/faq), [Ollama's model list API](https://docs.ollama.com/api/tags), and [Tailscale's device connection guide](https://tailscale.com/docs/how-to/connect-to-devices).

## Launch the local web interface

From the repository directory, use Python 3.10+:

```bash
python3 -m macromellow web
```

The server opens [http://127.0.0.1:8000/](http://127.0.0.1:8000/) in your browser. If a browser tab does not open automatically, visit that address yourself. Press `Ctrl+C` in the terminal to stop the server. Type a meal in the **Assistant** view and press Send. Enter sends; Shift+Enter adds a line. Use **New conversation** to clear the current context. The **Browse UMD data** tab provides the original manual search and source labels.

The app reads actual JSON files in this repository's `data/` directory. Data is not committed to Git, so a fresh clone starts empty: open **Browse UMD data**, choose today's date, and click **Refresh UMD data** to retrieve all three halls. A complete refresh can take several minutes; the page shows a loading state and any retrieval error. Existing saved data is kept if a refresh is incomplete. Dates outside UMD's current seven-day menu window cannot be refreshed, although older saved JSON can still be viewed. After a refresh, return to **Assistant** and ask about that date.

You can change the local port or data directory:

```bash
python3 -m macromellow web --port 8001 --data-dir /path/to/your/json-directory
```

Use `--no-browser` if you only want to start the server. The server listens on `127.0.0.1` only. It uses Python's standard library and needs no Python package installation step. All model requests go from the Python backend to Ollama; the browser never calls Ollama directly.

## Daily macro tracker

The **Today’s macros** strip stays above the assistant conversation. Open **Adjust totals manually** to add, subtract, or set any combination of calories, protein, carbs, and fat. Leave a field blank to keep it unchanged; zero is a valid direct value. The four totals are independent, and manual entries can be negative for testing corrections. **Reset to zero** clears the current day's totals.

Complete AI nutrition results have an **Add result to today** button. Answering a question does not change tracked totals until you press it. Each result button adds only once; an incomplete UMD result cannot be added automatically, but you can enter your own test values manually. A follow-up correction is a new result, so subtract any earlier result you already added before adding the correction.

The tracker stores only the current day's totals and used result IDs in this browser's `localStorage`. It starts at zero on the next **America/New_York** calendar day, including while the page stays open. Browser storage is separate by browser profile and local origin, so use the same browser and port to keep today's totals after refresh or server restart. The tracker has no account or food diary. Its values are **user-adjustable estimates** and may differ from official UMD values.

## Test the assistant

With a saved menu and the Windows Ollama server connected, try `I had 2 servings of grilled chicken breast at 251 North on 2026-10-19.` Substitute a date you have saved. Try a second message such as `Actually, make that 4 servings.` The displayed values should scale from the linked UMD label. Try `chicken at The Y` to see how the assistant handles a broad match. If the AI indicator is offline, the manual browser still works.

The assistant sends a constrained JSON schema to [Ollama's chat endpoint](https://docs.ollama.com/api/chat) and validates the response. The model extracts requested names, amounts, halls, and dates only. Python searches local saved menus, checks match confidence, multiplies official per-serving values, and sums nutrients. If a food description has multiple plausible menu matches, it asks for a specific name. If a counted or vague amount lacks a measured serving size, it assumes one listed UMD serving per count and displays that assumption. Missing official nutrient fields stay blank, including in the corresponding total. Conversations live in server memory only and reset when the server stops.

### Developer debugging

Open **Developer debugging** below any assistant response to inspect that turn. It shows the original request, the model's structured interpretation, the effective meal items after any follow-up correction, the saved date and hall used for each lookup, selected UMD label links, and ranked alternative records. The displayed name score is a **heuristic similarity score, not a probability** that the food is correct. A low score or a close competing record prevents automatic selection and asks for clarification. A different selected menu name or an assumed portion is called out in the normal response as well as the debug panel.

For each selected food, the panel shows UMD values per listed serving multiplied by the number of assumed servings, then the final total. Missing official values remain unavailable in both places. The panel also lists accuracy notes, the Ollama response time (including its model availability check), the full request time, and any error stage. Errors return a debug panel too. These diagnostics are sent only to the local browser for the current turn; they are not saved to the UMD JSON files.

Run the automated tests without a live Ollama server:

```bash
python3 -m unittest discover -s tests -v
node --test tests/test_tracker.cjs
```

## Command line retrieval and search

Python 3.10+ is required. There are no third-party Python dependencies.

```bash
python3 -m macromellow fetch --hall all --output data/latest.json
python3 -m macromellow search "chicken" --file data/latest.json
python3 -m macromellow search "tofu" --file data/latest.json --hall yahentamitsi
```

Omit `--date` to use today's date in Maryland. `--hall` accepts `all`, `south`, `yahentamitsi`, or `251-north`. The default output is `data/umd-YYYY-MM-DD.json`; use `--output` to choose another path. A full fetch follows all linked nutrition labels and may take several minutes. For a quick connectivity check, `--max-labels 3` fetches all requested menus but only three unique labels; skipped labels remain `null` and are recorded as errors. The command returns exit status 2 when the saved result has any errors, and 1 if it cannot start (for example, robots.txt cannot be checked).

Search reads a saved JSON file without making network requests. It displays matching food names, hall, date, meal, serving size, calories, protein, carbohydrates, fat, and the official label URL. Unknown values display as `unknown`.

## Data source and method

UMD's public menu page has an ordinary GET form with `locationNum` and `dtdate`. Its [public JavaScript](https://nutrition.umd.edu/js/custom.js) uses those fields to change the displayed menu and offers a rolling seven-day date selector. The form lists hall IDs 16 (South Campus), 19 (Yahentamitsi), and 51 (251 North). Each menu item links to an individual `label.aspx?RecNumAndPort=...` page. The prototype reads the menu HTML, follows those official links, and extracts the primary Nutrition Facts panel's serving size, calories per serving, total fat, total carbohydrate, and protein. It stores the menu and label URLs with every item. A repeated label URL is fetched only once per run.

I found no publicly documented nutrition API on the official site during the initial investigation (October 19, 2026). This prototype uses the site's public HTML; it does not use a private endpoint or bypass an access restriction. The site's `/robots.txt` returned HTTP 404 when checked. At run time, the program checks it again: explicit disallow rules are honored, while unexpected failures stop retrieval. Requests are sequential with at least 0.25 seconds between them; HTTP 403 or 429 stops the run. The default delay can be increased with `--delay`.

## JSON format

The JSON file contains `schema_version`, `source`, `menu_date`, `retrieved_at`, `foods`, and `errors`. Each `foods` entry contains `dining_hall`, `menu_date`, `meal`, `station`, `name`, `serving_size`, `calories`, `protein_g`, `carbohydrates_g`, `fat_g`, `menu_url`, `source_url`, and `retrieved_at`. Nutrients are **per listed serving**, not per meal. A food can appear more than once if UMD lists it at multiple meals or stations. Numeric fields and serving size are `null` when unavailable; `errors` records inaccessible pages and parsing failures. Saved data is excluded from Git because menus change and a full scrape is relatively large.

## Limits

- UMD's date picker offers today plus six days. Other dates may have no menu; the program reports an empty menu instead of assuming one.
- UMD notes that its nutritional analysis is approximate and can vary with ingredients and preparation. See an [official label](https://nutrition.umd.edu/label.aspx?RecNumAndPort=119370%2A1).
- The parser depends on UMD's current HTML structure. If UMD changes it, fields may become `null`; whole-label parsing failures appear in `errors`. Verify against the site before using the data in another product.
- A partial file may be saved when a request fails. Inspect `errors` before treating a dataset as complete.
- On October 19, 2026, six distinct official labels explicitly said nutrition information was unavailable. They account for 14 menu appearances with `null` nutrition fields in the saved test dataset.
- A menu item may not exist at the requested hall or date. For example, the saved October 19 and 20 menus do not list a chicken breast at The Y. The assistant will request a more specific item or another date instead of using a different chicken dish silently.
- This prototype uses name-based matching against local saved data, not ingredient recognition. Official menus can contain similar dishes; inspect the linked label when a selection matters.
